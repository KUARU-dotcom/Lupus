# ERRATA к спецификации Lupus V1.0 (Rust-реализация)

Документ фиксирует осознанные отступления Rust-интерпретатора от
`docs/specification-v1.0.md`. Все пункты — решения владельца проекта, а не
дефекты реализации. При расхождении спеки и этого файла приоритет имеет
данный документ.

## 1. Модули и импорт

- **Одноуровневый импорт по умолчанию.** `(import senko)` импортирует пакет
  `senko`, префикс квалифицированных имён — `senko/` (например,
  `(senko/sqrt 25.0)`). Форма `(import (senko math))` из спеки сохранена для
  мультимодульных пакетов: префиксом становится имя модуля (`math/`). В V0.5
  использовались только одноуровневые импорты; в V0.6 канонические импорты
  `texas` и `amiya` используют второй уровень (`(import (texas net) :as net)`,
  `(import (amiya async) :as async)`).
- **`:as` переопределяет префикс.** `(import senko :as math)` даёт `math/`.
- **`:all`** импортирует имена без префикса; конфликт с уже существующим
  именем — линт-ошибка `import-collision`.
- **Пакеты V0.5:** нативные `senko` (математика), `kaltsit` (файлы), `w`
  (тесты). В V0.6 добавлены `texas` (сеть), `lappland` (инъекция отказов) и
  `amiya` (async); `exusiai` (Tensor) — V2.0. Коды ошибок модулей именуются по
  пакетам; runtime-коды ядра — из каталога §6 спеки.
- **Поиск модулей:** нативный реестр → `stdlib/<имя>.lupus` → каталоги из
  переменной окружения `LUPUS_PATH`.
- **Файловые модули** выполняются один раз (кэш по каноническому пути) и
  экспортируют только имена, объявленные через `define-public`. Цикл импортов
  диагностируется кодом `import-cycle` (расширение каталога §6).

## 2. FFI

- **Python-FFI объявлен заменённым** нативными модулями. Директива
  `(#lupus ffi python "...")` диагностируется как `invalid-directive` с
  подсказкой о переходе на `(import senko)` / `(import kaltsit)` / `(import w)`.
  Коды `ffi-*` из §6.2 в V0.5 не выдаются.

## 3. Ошибки

- **stderr всегда содержит строгий JSON** по §6.1. Флаг `--pretty` печатает
  человекочитаемый рендер того же JSON в stderr; stdout остаётся чистым
  выводом программы.
- **`location` присутствует при наличии span у узла AST.** Это относится к
  `lex`/`parse`, а также к `runtime`/`lint`/`type`-ошибкам, возникшим при
  вычислении узла. `location = null` остаётся только для ошибок без
  привязки к исходнику: `io-error` до разбора/запуска, отказ spawn,
  `no-tests-found`.
- **Строки в JSON-ошибках** всегда экранируются по правилам JSON; переводы
  строк в `message`/`context` кодируются как `\n`, а не как сырые символы.
- **`io-error` (phase `runtime`)** — ошибка чтения основного файла программы
  (файл отсутствует или недоступен). Код `unknown-module` зарезервирован
  только за резолвом `import` (нативные пакеты, `stdlib`, `LUPUS_PATH`).
- **Новые коды V0.5** (расширение каталога §6.2):
  `import-cycle`, `math-domain-error`, `const-non-literal`.
- Код `match-redundant` не выдаётся: статический анализ избыточности паттернов
  появится вместе с HM-тайпчекером в следующих версиях.
- Код `value-restriction` не выдаётся: ограничение значений относится к HM.
- Код `runtime/exhausted` в V0.5 не использовался; в V0.6 он выдаётся
  лимитами kennel (см. §17).

## 4. Синтаксис и семантика

- **Одиночная `;` начинает комментарий** до конца строки (наравне с `;;`).
  Иначе лексер зацикливался бы на одиночном символе `;`.
- **`nth` не возвращает `Option`.** По решению владельца `(nth список индекс)`
  возвращает сам элемент, а выход индекса за границы — runtime-ошибка
  `index-out-of-bounds`. Это сознательное отклонение от §2.2/§3.1.
- **Унарный минус для float** записывается как `(- x)` или `(- 0.0 x)`.
  Отрицательных float-литералов в исходнике нет (лексер разбирает `-3` как
  целое, а `-3.5` — как символы `-` и `3.5`).
- **`define-const`** семантически совпадает с `define` (неизменяемая связь).
  Линт `const-non-literal` предупреждает, если значение не литерал.
- **Tensor** не реализован; типы и операции появятся в V2.0 вместе с пакетом
  `exusiai`.

## 5. Типы и дженерики

- HM-тайпчекер в V0.5 отсутствует. Проверяются только синтаксические
  требования `define-public` (`missing-return-type`, `missing-param-type`).
  Аннотации параметров и полей `defstruct` парсятся, но не проверяются.
- **Параметры дженерик-структур** — идентификаторы; регистр не проверяется
  (`a`, `T`, `Element` равноправны). `(Option (Node a))` в полях парсится как
  `type_expr` без унификации.
- `Map` хранится как упорядоченный по вставке список пар; ключом может быть
  любое сравнимое значение, кроме `Float`-NaN.

## 6. Прочее

- Песочница, kennel/host-API и лимиты выполнения появились в V0.6
  (см. §17).
- Директивы `#lupus` кроме документированных в спеке распознаются как
  `invalid-directive`.

## 7. V0.5-rc2: лимиты глубины

- **`stack-depth-exceeded` (phase `runtime`).** Глубина
  вызовов пользовательских функций и замыканий ограничена 10 000. Builtins и
  нативные функции в счётчик не входят. При превышении возвращается ошибка
  «Превышена максимальная глубина рекурсии (10000). Проверьте условие выхода.».
- **`nesting-too-deep` (phase `parse`, `location` со `span`).** Вложенность
  скобок ограничена 1 000. При превышении возвращается ошибка «Слишком глубокая
  вложенность скобок (>1000).»; `span` указывает на открывающую скобку,
  которая превысила лимит.
- Для легальной рекурсии до 10 000 вызовов CLI выполняет вычисление в
  отдельном потоке с увеличенным стеком (tree-walk eval в debug-сборке
  расходует много стека на вызов). Логический лимит при этом не меняется.

## 8. V0.5-rc2: арифметика и exit

- **`integer-overflow` (phase `runtime`).** Целочисленные
  `+`, `-`, `*`, `/`, `%`, унарный `-`, `abs` и `pow` используют checked-операции.
  Переполнение возвращает `integer-overflow`, а не `type-mismatch` и не панику.
- **`divide-by-zero` (phase `runtime`).** Для целочисленных `/` и `%` нулевой
  делитель даёт `divide-by-zero`. Переполнение `MIN / -1` и `MIN % -1` —
  `integer-overflow`.
- **`invalid-exit-code` (phase `runtime`).** `(exit n)` принимает только
  `0..=255`; другой код — runtime-ошибка, процесс не завершается с этим кодом.
- **`int->float` выше 2^53.** Конверсия теряет точность для целых больше
  `2^53` — это намеренная семантика IEEE 754 binary64, а не ошибка.

## 9. V0.5-rc2: oracle-дифференциал

> **Префиксное сравнение stdout для exit≠0.** V0.4.0 печатал диагностику
> в stdout, V0.5 — JSON в stderr. Для ошибочных программ oracle сравнивает
> stdout по префиксу (`expected.stdout.starts_with(actual.stdout)`), чтобы
> игнорировать хвост диагностики. Для exit 0 сравнение байт-в-байт.
> Расхождение в хвосте текста ошибки дифференциалом не ловится.

- Корпус включает все `tests/golden/*.lupus` и `examples/*.lupus`; файлы с
  конструкциями V0.5 (`import`, `Map`, дженерики, `test`, новые escape)
  помечаются SKIP. Дополнительно генерируются 60 детерминированных программ
  (seed=42, 42 успешных / 18 с ошибкой) в `target/oracle_corpus_seed42`.

## 10. V0.5.1: аудит и Unicode-идентификаторы

- **`no-tests-found` (phase `runtime`, `location = null`).** `lupus test`
  завершается с кодом 1, если в файле или каталоге не найдено ни одного теста.
  Сообщение: «в <path> не найдено ни одного теста». `test-summary` с `total=0`
  не считается успехом. Пустой каталог и файл без форм `(test ...)` — ошибка.
- **`invalid-escape` (phase `lex`, `location` с позицией).** Неизвестная
  escape-последовательность (например, `\q`) и некорректный `\u`/`\x` дают
  `invalid-escape`. Одинокий суррогат (`\uD83D` без младшего) — тоже
  `invalid-escape`; корректная суррогатная пара (`\uD83D\uDE00`) собирается в
  один Unicode scalar (`😀`).
- **Код выхода 2 — ошибка использования CLI.** Неизвестный флаг (`lupus
  --нет-флага`, `lupus run --нет-флага f.lupus`) печатает plain-text usage в
  stderr и завершается с кодом 2. Это не JSON-диагностика языка и не код 1.
  Коды 0/1 остаются для успеха и ошибок программы/линта/тестов.
- **`Location.col` считается в символах, `span` — в байтах.**
  `col = line[..byte].chars().count() + 1`; кириллица и эмодзи перед ошибкой
  учитываются как один символ. Байтовые `start`/`end` в `span` не меняются.
- **BOM (U+FEFF) в начале источника пропускается.** Лексер начинает разбор
  после BOM; BOM в середине файла остаётся `unknown-token`.
- **§1.1 расширен: IDENTIFIER допускает Unicode alphabetic (ревизия спеки
  1.1).** Первый символ идентификатора — `char::is_alphabetic()` или `_`;
  продолжение — alphabetic / decimal digit / `_` / `-`. Ключевые слова остаются
  ASCII. Emoji не являются alphabetic и дают `unknown-token` (например,
  `(define 🐺 1)`). `/` не входит в алфавит идентификатора; квалифицированные
  имена (`senko/sqrt`) по-прежнему лексерятся одним токеном.
- **Захват переменных в циклах — две семантики.**
  `while`: тело выполняется в том же окружении, поэтому замыкания видят
  финальное значение переменной (позднее связывание, как `while` в Python).
  `for`: на каждую итерацию создаётся свежее дочернее окружение, поэтому
  замыкания захватывают значение своей итерации (как `let` в `for` в JS).
  См. [§1.3 спецификации, «Захват переменных в циклах»](./specification-v1.0.md#13-примечания-к-грамматике)
  (дополнение рев. 1.1).

## 11. Лексер: `/` в символьном токене

> **Лексер: `/` в символьном токене.** Лексер сохраняет `/` внутри символьного
> токена (`senko/sqrt` лексится одним токеном), хотя спека §1.1 требует разбора
> qualified-имени на этапе парсера (IDENT, SLASH, IDENT). Семантика идентична;
> рефакторинг токенизации отложен до V0.6.

## 12. V0.5.2: дельта-аудит NikoGPT

- **BUG-45: комбинирующие знаки только в продолжении идентификатора.**
  Диапазоны Mn/Mc из компактной таблицы (`src/unicode_marks.rs`) допускаются
  после первого символа имени, но не в начале: `(define ко́фе 1)` и NFD-имя
  `cafe` + U+0301 корректны, а комбинирующий знак первым символом даёт
  `unknown-token`. Исходник не нормализуется: NFC и NFD — разные
  идентификаторы. Полные таблицы Unicode и NFC-нормализация — бэклог V1.0
  (BUG-45). Имена файлов модулей рекомендуется держать ASCII, чтобы не
  зависеть от формы нормализации.
- **BUG-46: exit 2 — любая ошибка использования CLI.** Отсутствие
  позиционного файла/выражения, лишние позиционные аргументы, флаг без
  команды и вызов без аргументов печатают plain-text usage в stderr и
  завершаются с кодом 2; stdout пуст, JSON-диагностики нет. Неизвестные флаги
  идут по тому же пути. Это не ошибки программы/линта (код 1). Штатный
  `--help`/`-h` остаётся отдельным успешным путём (usage в stdout, код 0).
  Usage при ошибках всегда в stderr.
- **BUG-47: однодефисные флаги.** Токен, начинающийся с `-` и буквы (`-x`,
  `-я`), считается неизвестным флагом: usage в stderr, код 2. Одиночный `-`
  и `-` с цифрой (`-1`) остаются позиционными аргументами.
- **BUG-48: буквенный хвост числа.** Если сразу после числового токена идёт
  символ identifier-start (alphabetic или `_`), лексер выдаёт `unknown-token`
  с позицией: `1a` — ошибка, а `1.5e3` и `2` — корректные числа. Разделённые
  пробелом `1 a` остаются двумя токенами (например, `arity-mismatch`).
- **By design: `char::is_alphabetic()` включает Nl в начало идентификатора.**
  Символы категории Nl (например, `Ⅴ`) допустимы как первый символ имени.
  Это совпадает с UAX31 (ID_Start включает Nl) и поведением Python.
- **`lupus eval` и модули (#35).** `lupus eval` вычисляет одно выражение в
  окружении только с core-биндингами. В V0.6 добавлен явный пре-импорт
  `lupus eval --import w,senko "<expr>"`; без флага поведение прежнее
  (см. §17.5). Для остальных сценариев с модулями — `lupus run`.


## 13. V0.6 этап 4: `and`/`or`, политика типов, `defstruct`

> Раздел фиксирует ревизию семантики V0.6. Он дополняет §1.3 и §2 спеки V1.0;
> в случае расхождений приоритет имеет этот раздел.

### 13.1. `and` и `or` возвращают значение

- `(and a b c)` вычисляет аргументы слева направо с коротким замыканием:
  если все истинны — возвращает значение последнего; иначе — первое ложное.
- `(or a b c)` вычисляет аргументы слева направо с коротким замыканием:
  возвращает первое истинное значение; если истинных нет — последнее ложное.
- `(and)` → `true`, `(or)` → `false`. Это расширение: §1.3 спеки V1.0
  требовал 2+ аргумента.
- Ложны только `false` и `none`. `0`, `0.0`, `""`, `()`, пустые `Map`/`Tuple`
  и `failure` истинны. Это заменяет прежнюю Python-подобную истинность V0.5.
- Короткое замыкание сохраняется: `(and false (/ 1 0))` не вычисляет деление
  и возвращает `false`; `(or true (/ 1 0))` возвращает `true`.

### 13.2. Единая политика типов builtins

| Ситуация | Код ошибки | Примеры |
|----------|------------|---------|
| Аргумент не того типа в builtin | `type-mismatch` | `(empty? 5)`, `(contains? 5 "x")`, `(length 5)`, `(nth "str" 0)` |
| Доступ в пустой контейнер | `index-out-of-bounds` | `(head ())`, `(tail ())` |
| Индекс вне диапазона | `index-out-of-bounds` | `(nth (list 1 2) 5)` |
| Не-контейнер в доступе | `type-mismatch`, не `none` | `(head 5)`, `(tail 5)`, `(nth "str" 0)` |

`head`/`tail` больше не возвращают `none` молча для пустого списка или
не-списка. `tail` от списка из одного элемента по-прежнему возвращает `none`
(это не доступ в пустой контейнер, а отсутствие хвоста). Политика применяется
ко всем builtins: неверный тип аргумента — всегда `type-mismatch`.

Литерал `()` теперь означает пустой список (наряду с `(list)`), а не пустой
вызов, возвращавший `none`. Это делает `(head ())` и `(tail ())` доступом в
пустой контейнер и обеспечивает требуемый `index-out-of-bounds`; `(empty? ())`
возвращает `true`, а `()` истинно как пустой список.

### 13.3. Конструктор `defstruct` проверяет типы полей

- Для полей с конкретными типами конструктор проверяет аргументы:
  `(defstruct point (x int) (y int))` принимает `(point 1 2)` и отвергает
  `(point "a" 1)` с `type-mismatch`.
- Сообщение содержит имя поля и ожидаемый тип:
  `поле x: ожидался int`.
- Поддерживаются `int`, `float`, `bool`, `str`, `none`/`unit`, а также
  составные `(List t)`, `(Option t)`, `(Result t e)`, `(Tuple ...)`,
  `(Map k v)`; вложенные компоненты проверяются рекурсивно.
- Параметры дженерик-структур принимают значение любого типа:
  `(defstruct (Box a) (value a))` допускает `(Box 42)`, `(Box "hi")` и
  `(Box (list 1 2))`. Параметр внутри составного типа также является
  wildcard-ом.
- Неизвестные именованные пользовательские типы не проверяются: HM-тайпчекера
  в V0.6 нет. Это не отменяет проверку известных скалярных и составных типов.
- Проверка выполняется после проверки арности; при нескольких неверных полях
  сообщение относится к первому полю в порядке объявления.

## 14. V0.6 этап 5: консервативный mark-and-sweep GC

> Раздел фиксирует поведение сборщика мусора V0.6. Он дополняет §6 и §13;
> при расхождении приоритет имеет этот раздел.

- **Запуск по порогу аллокаций.** Счётчик атомарный. Аллокацией считаются
  созданные окружения (`Environment::new` / `new_child`) и замыкания
  (`lambda`, `define` с функциональной формой). При достижении порога
  автоматически выполняется полная сборка. По умолчанию порог равен 1000
  (`gc::GC_THRESHOLD`); переменная окружения `LUPUS_GC_THRESHOLD` задаёт
  положительное целое `N`, а невалидное значение, `0` или отрицательное число
  оставляют значение по умолчанию. Переменная читается один раз за процесс.
  Встраивание может вызывать `(gc-collect)` вручную.
- **Корни.** Глобальное окружение интерпретатора, активные кадры вызовов,
  кэш/импорты модулей и значения, удерживаемые хостом, считаются корнями.
  Консервативность означает, что любая сильная `Rc`-ссылка, не объяснимая
  ссылками из других зарегистрированных окружений, сохраняет окружение
  живым. Rust-стек не сканируется побайтово; ложных освобождений нет.
- **Mark/sweep.** Mark обходит окружения, `bindings`, `parent` и замыкания в
  списках, `Map`, `Tuple`, структурах, `some`/`success`/`failure`. Sweep
  очищает `bindings` и `parent` недостижимых окружений. Это разрывает циклы
  `env → list/map → closure → env`; после этого обычный `Rc` освобождает
  память. Циклы без окружений (например, самоссылающийся список) в языке
  невозможны из-за иммутабельности контейнеров.
- **Пауза.** На типичных программах прототипа пауза сборки <10 мс; на
  тестовом графе из 20 000 живых замыканий release-сборка трассирует его за
  ~8.3 мс (debug-сборка ожидаемо медленнее). При очень больших живых графах
  пауза линейна по числу зарегистрированных окружений и значений; для
  долгоживущих программ рекомендуется периодически вызывать `(gc-collect)` в
  удобной точке, а не полагаться только на порог.
- **Логирование.** При автоматической сборке строка
  `GC: collected N objects, freed M bytes` печатается в stderr, только если
  `N > 0`; `(gc-collect)` печатает её всегда. Формат стабилен для парсеров,
  но сами числа — приблизительная оценка (окружения + связи, байты по
  ёмкости контейнеров).
- **`(gc-collect)`** — встроенная функция с арностью 0. Возвращает `none`.
  Она безопасна в любой точке вычисления: значения на Rust-стеке
  консервативно считаются внешними корнями.
- **Ограничения.** Сборщик не является точным: временные значения и внешние
  `Rc` могут задерживать освобождение до следующего вызова. Он не заменяет
  HM-тайпчекер и не управляет памятью нативных модулей (`kaltsit`), которая
  освобождается штатным `Drop`.

## 15. V0.6 этап D: `texas` (net) и `lappland` (инъекция отказов)

> Раздел фиксирует поведение сетевого пакета и управляемой инъекции ошибок.
> Канонические сигнатуры `texas` взяты из §3.3 спецификации; в случае
> расхождений приоритет имеет этот раздел.

- **Пакеты и импорт.** `texas` и `lappland` — нативные пакеты V0.6.
  Канонический импорт: `(import (texas net) :as net)`; после него доступны
  `net/tcp-connect`, `net/tcp-listen`, `net/accept`, `net/send`, `net/recv`,
  `net/recv-line`, `net/close`, `net/udp-bind`, `net/udp-send-to`,
  `net/udp-recv-from`. Также работают `(import texas)` с префиксом `texas/` и
  короткие алиасы `tcp-accept`, `tcp-send`, `tcp-recv`, `udp-socket`,
  `udp-send`, `udp-recv` с теми же арностями и семантикой.
- **Result-значения, не исключения.** Ошибки сети и DNS возвращаются как
  `(failure "net: ...")`; программа продолжает выполняться и обычно
  завершается с кодом 0. Неверный тип аргумента — по-прежнему
  `type-mismatch` (исключение интерпретатора). `net/close` возвращает `unit`.
- **Таймауты.** `tcp-recv`, `tcp-recv-line` и `udp-recv-from` устанавливают
  read timeout 5 секунд. Истечение таймаута — ровно
  `(failure "net: timeout")`; прочие ошибки — `(failure "net: <io error>")`.
  `tcp-connect` и `tcp-accept` отдельного таймаута не имеют.
- **Opaque-значения.** `tcp-connect`/`udp-bind` возвращают `Value::Socket`,
  `tcp-listen` — `Value::Listener`. Это непрозрачные значения: их нельзя
  создать из Lupus напрямую, сравнивать можно только по идентичности объекта,
  печать даёт `socket`/`listener`. Они **не сериализуются** в `SendValue`
  (этап E): попытка маршалинга должна давать `type-mismatch`. `accept`
  принимает только `Listener`; `send`/`recv` — только TCP-socket,
  `udp-send-to`/`udp-recv-from` — только UDP-socket.
- **`lappland/malice p`.** Аргумент — строго `float` в диапазоне
  `0.0..=1.0`; иначе `type-mismatch`. Задаёт вероятность инъекции отказа для
  последующих `texas`-вызовов в текущем лексическом окружении и его потомках.
  Настройка перекрывает родительскую; независимые интерпретаторы её не
  наследуют. При срабатывании Result-функция возвращает
  `(failure "net: injected malice")` до выполнения сетевой операции.
  `net/close` не инжектируется, так как возвращает `unit`.
- **`lappland/delay k`.** Аргумент — строго `float >= 1.0`; иначе
  `type-mismatch`. Дополнительная задержка каждого последующего net-вызова
  равна `10 мс * (k - 1)`, поэтому `k = 1.0` ничего не добавляет. Задержка
  применяется и к `close`; инъекция — только к функциям, возвращающим Result.
- **Детерминизм.** `LUPUS_MALICE_SEED` принимает целое `u64` или произвольную
  строку (FNV-1a) и инициализирует xorshift64* для проверки вероятности.
  Одинаковый сид даёт одинаковую последовательность результатов при одинаковой
  последовательности вызовов. Если переменная отсутствует, используется
  энтропия (время + pid); такие прогоны не воспроизводимы. При `p = 0.0` и
  `p = 1.0` ГПСЧ не расходуется.
- **UDP-адресация.** `udp-bind` слушает `0.0.0.0:<port>`; получить выбранный
  эфемерный порт из языка нельзя (в §3.3 нет `local-port`), поэтому реальные
  UDP-тесты используют заранее выбранный высокий порт. `udp-recv-from`
  возвращает `(host, port, data)`.
- **Пример `examples/v06_net.lupus`.** Создан на этапе E: TCP echo, сервер в
  фоновой задаче `amiya/spawn`, клиент в главном потоке. Порт по умолчанию
  `47711`; интеграционный прогон подставляет `LUPUS_EXAMPLE_PORT` в исходник
  перед запуском, потому что в §3.3/§3.5 нет функции чтения окружения.
  Сетевые сценарии также покрыты интеграционными тестами `tests/net.rs` и
  golden-тестом `v06_net`.

## 16. V0.6 этап E: `amiya` (async), маршалинг и каналы

> Раздел фиксирует поведение пакета `amiya` и границы потоков. Канонические
> имена взяты из §3.5; `join`/`await` в спецификации отсутствуют и не
> добавлялись.

- **Пакеты и импорт.** `amiya` — нативный пакет V0.6. Канонический импорт:
  `(import (amiya async) :as async)`. Доступны ровно `async/spawn`,
  `async/sleep`, `async/channel`, `async/send`, `async/recv`,
  `async/recv-timeout`, `async/wait`, `async/wait-all`.
- **Канал.** `async/channel` возвращает пару `(tuple sender receiver)`.
  `async/send` и `async/recv` принимают как всю пару (совместимость с
  примерами §3.5, где один `ch` используется для обеих операций), так и
  отдельный `sender`/`receiver`. Закрытие канала — это удаление последнего
  `sender`; отдельного `close` в §3.5 нет.
- **Закрытый канал.** `async/recv` на канале без живых отправителей
  возвращает значение `(failure "async: closed")` (не исключение). То же
  значение возвращает `async/send`, если получателей больше нет.
  `async/recv-timeout` возвращает `none` по таймауту, `(some v)` при получении
  и `(failure "async: closed")` при разрыве; это осознанное расширение
  `Option a`, зафиксированное здесь.
- **`async/spawn`.** Принимает только замыкание без параметров. Задача
  обязана вернуть `unit`; любое другое значение, включая `socket`, `listener`
  или `task`, даёт `type-mismatch`, который пробрасывается из
  `async/wait`/`async/wait-all`. Ошибка/паника внутри задачи также
  обнаруживается при ожидании.
- **Снимок окружения.** Захваченное замыканием окружение глубоко копируется
  в момент `spawn`. Последующие `set!` в исходном окружении задачу не видят.
  Каналы передаются как разделяемые handles: сообщения, отправленные после
  `spawn`, видны обеим сторонам.
- **Что переносится.** Числа, строки, списки, кортежи, Map, структуры,
  `some`/`success`/`failure`, замыкания, нативные функции, `sender` и
  `receiver` маршалируются через `SendValue` (`Arc`/`Mutex`). Вместе со
  снимком задачи переносятся импорты и реестр `defstruct`.
- **Что не переносится.** `socket`, `listener` и `task` не имеют
  `SendValue`-представления. Явная передача такого значения в
  `async/send` или возврат из задачи даёт `type-mismatch`. При снимке
  окружения такие неиспользуемые связи пропускаются, чтобы одна `task` в
  глобальном окружении не мешала запускать следующую; если задача всё же
  обратится к пропущенному имени, она получит `unknown-identifier`.
- **Параллельность.** Каждая задача — отдельный поток ОС. `async/sleep`
  блокирует только текущий поток, поэтому две задачи по 100 мс выполняются
  параллельно; `async/wait`/`async/wait-all` блокируют вызывающий поток до
  завершения задач. `async/recv` блокирующий, без busy-wait.
- **`async/wait-all`.** Принимает список `task`, ждёт все задачи и
  возвращает `unit`; первая ошибка (в порядке списка) пробрасывается после
  ожидания остальных.
- **Примеры.** `examples/v06_async.lupus` — spawn + канал без сети;
  `examples/v06_net.lupus` — TCP echo с сервером в задаче.

## 17. V0.6 этап F: kennel, профили, fuel и `eval --import`

> Раздел фиксирует публичный host-API встраивания, профили возможностей и
> лимиты выполнения. CLI по умолчанию работает на профиле `full` без лимитов,
> поэтому golden/negative-тесты и примеры этапов A–E не меняют поведение.

### 17.1. Публичный API `kennel`

- `lupus::kennel::run_program(source, &Config, &Host) -> Result<String, JsonError>`
  создаёт изолированный интерпретатор, выполняет исходник и возвращает весь
  вывод `(print ...)` как строку. Линт при встраивании не запускается.
- `Config` содержит `profile`, `max_steps`, `max_memory_values`, `max_depth` и
  `fuel`. `Config::default()` — профиль `Full` без лимитов, как CLI.
- `Host::register_native(name, arity, function)` регистрирует функцию
  `fn(&[Value]) -> Result<Value, String>`. Из Lupus она вызывается как
  `host/<name>` без отдельного `import`. Префикс `host/` в имени при
  регистрации допускается.
- Ошибка `Err(String)` из host-функции становится runtime-ошибкой
  `host-error`; неверная арность — обычной `arity-mismatch`. Если функция не
  зарегистрирована, `host/<name>` даёт `unknown-module-symbol`.
- `JsonError` оборачивает `Error` и предоставляет `code()`, `message()`,
  `to_json()` и `to_json_value()`; `Deref<Target = Error>` сохранён для
  доступа к остальным полям диагностики.

### 17.2. Профили

| Профиль | Core-биндинги | `kaltsit` | `senko`/`w` | `texas`/`amiya`/`lappland` | host |
|---------|---------------|-----------|-------------|----------------------------|------|
| `pure`  | да            | нет       | нет         | нет                        | нет  |
| `core`  | да            | да        | нет         | нет                        | нет  |
| `full`  | да            | да        | да          | да                         | да   |

- `pure` — только имена ядра; любая форма `import` (включая файловые модули)
  запрещена.
- `core` — ядро и нативный `kaltsit`; файловые модули разрешены, но их
  собственные импорты проходят ту же проверку профиля. Остальные нативные
  пакеты запрещены.
- `full` — все нативные пакеты и зарегистрированные host-нативы. Это профиль
  CLI.
- Нарушение даёт runtime-ошибку `profile-denied`; сообщение содержит имя
  запрещённого пакета (`texas`, `amiya`, `host` и т.п.). Проверка выполняется
  до резолва файла/пакета и до выполнения импортируемого модуля.
- Квалифицированное имя запрещённого нативного пакета без `import`
  (`(texas/tcp-connect ...)`) также даёт `profile-denied`, а не
  `unknown-identifier`.

### 17.3. Fuel (лимит шагов)

- Счётчик шагов находится в `eval`-цикле: каждая форма-список (вызов
  функции, специальная форма, включая пустой `()`), а также итерация
  `while`/`loop` списывает один шаг. Атомарные литералы и символы внутри
  формы отдельного шага не стоят, но рекурсия и циклы всё равно ограничены,
  потому что каждое тело/итерация проходит через форму-список или явный
  счётчик итерации.
- `Config.max_steps` и `Config.fuel` — два имени стартового бюджета; если
  заданы оба, действует меньшее значение.
- CLI читает `LUPUS_FUEL=N`. Допустимо только целое `N > 0`; невалидная
  строка, отрицательное число или `0` означают отсутствие лимита и не дают
  паники. Без переменной лимита нет.
- Исчерпание бюджета — runtime-ошибка `exhausted` с сообщением о лимите
  шагов. Она печатается как обычная JSON-диагностика, код выхода CLI — 1.
- `(set-fuel! n)` — специальная форма, доступная во всех профилях. Она
  **только уменьшает** установленный потолок: `n` не может быть больше
  когда-либо установленного лимита. При отсутствии лимита форма создаёт его
  равным `n`. Повторение прежнего значения разрешено, но остаток не
  увеличивается. Попытка поднять потолок — runtime-ошибка
  `fuel-raise-denied`; нецелый или отрицательный `n` — `type-mismatch`.
- Бюджет хранится в `Arc` с атомарными остатком и потолком и является общим
  для задач `amiya/spawn`: задача не может обойти лимит, созданный до запуска.
  Если лимит не был задан, `(set-fuel! n)` внутри задачи создаёт локальный
  бюджет этой задачи.

### 17.4. `max_memory_values` и `max_depth`

- `Config.max_memory_values` — приблизительный накопительный счётчик
  heap-значений, возвращаемых формами-списками (вызовами и специальными
  формами): списки/кортежи/Map/структуры учитываются с вложенными элементами,
  строки и замыкания — за единицу. Это не точный размер живого графа GC, а
  консервативная оценка для песочницы.
  max_memory_values — накопительная квота аллокаций, не размер живой памяти; счётчик не уменьшается при GC.
  Превышение даёт `exhausted`.
- `Config.max_depth` заменяет стандартный предел 10 000 вызовов
  пользовательских функций. Превышение по-прежнему даёт
  `stack-depth-exceeded`, но в сообщении указывается настроенное `N`.
  Builtins, нативные функции и host-нативы в счётчик глубины не входят.

### 17.5. `lupus eval --import`

- `lupus eval --import w,senko "<expr>"` пре-импортирует перечисленные через
  запятую пакеты в окружение выражения. Каждый пакет импортируется обычной
  формой `(import <пакет>)`, поэтому доступны префиксы `w/` и `senko/`.
- Флаг можно повторять; `--import=w,senko` эквивалентен раздельной записи.
- Без флага `lupus eval` по-прежнему видит только core-биндинги;
  `(senko/sqrt 16.0)` без импорта даёт прежнюю ошибку `unknown-identifier`.
- Конфликт имён при импорте (в том числе `:all` внутри выражения) даёт
  штатную `import-collision`. Ошибка резолва пакета — `unknown-module`.
- `--import` допустим только для `lupus eval`; для других подкоманд это
  ошибка использования CLI (код 2).

### 17.6. Новые коды этапа F

| Код | Фаза | Значение |
|-----|------|----------|
| `profile-denied` | runtime | Профиль запретил пакет/возможность |
| `fuel-raise-denied` | runtime | `set-fuel!` пытается повысить потолок |
| `exhausted` | runtime | Исчерпан fuel или `max_memory_values` |
| `host-error` | runtime | Host-функция вернула `Err(String)` |

`exhausted` и `stack-depth-exceeded` используют существующие коды каталога
§6.2; `profile-denied`, `fuel-raise-denied` и `host-error` — расширения этого
каталога, зафиксированные здесь.

## BREAKING CHANGES V0.6

- `and`/`or` возвращают значение, а не только булево: `(and 1 2)` → `2`,
  `(or false "x")` → `"x"` (ERRATA §13.1).
- `()` — литерал пустого списка, а не `none`; `(empty? ())` → `true`
  (ERRATA §13.2).
- `head`/`tail`/`nth`/`empty?`/`contains?`/`length` на неверном типе дают
  `type-mismatch`, а не `none`; доступ в пустой контейнер даёт
  `index-out-of-bounds` (ERRATA §13.2).
- Конструкторы `defstruct` проверяют конкретные типы полей и отвергают
  неверные аргументы с `type-mismatch` (ERRATA §13.3).

Дифференциальный oracle v0.4.0 не является эталоном для перечисленных
изменений. Пропуски зафиксированы в `tests/oracle.rs` (`skip_reason`), поэтому
oracle-гейт проверяет совместимое подмножество, а V0.6-семантика закреплена
golden/negative-тестами LiF.
